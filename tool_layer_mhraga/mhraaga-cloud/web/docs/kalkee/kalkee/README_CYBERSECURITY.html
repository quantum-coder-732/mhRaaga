Cybersecurity — the security layer, the RL learning on top of it, and test results

The full walkthrough of app/security_guard.py (deterministic 🟢/🟡/🔴 classification), app/security_optimizer.py (the RL layer that learns from real confirmation outcomes on top of it), the Gmail/Calendar/Chat confirmation gate, and every test result behind the claims below. The main README.md has the shorter "Security layer" + "Security Prompts" sections inline in the chat-widget walkthrough; this file is the complete, standalone reference — start here if security is what you're evaluating.

Worth knowing if you're comparing against other frameworks: none of CrewAI, Microsoft's AutoGen/AG2, LangGraph Platform, OpenRouter, or LiteLLM ship a built-in security-scanning agent (real SAST, a real vulnerability database lookup, cloud-config scanning) or a live conversational security-flag layer like the one this file describes — verified against each project's own current documentation, not assumed. See README.md's "How Kalkee compares" table for the full, side-by-side breakdown.

Two layers, two different jobs

  1. security_guard.py — deterministic, the sole authority. Pattern matching (regex rules, each with a stable SEC-* id) over every real text surface a turn touches: the user's own prompt, and content read FROM Gmail/Calendar/Chat/MCP tools once it's rendered into the reply. Produces one of three flags — never an LLM guessing at its own safety, so the result is reproducible for automated testing. See README_REINFORCEMENT_LEARNING.md's security-optimizer diagram for exactly where this sits in a turn.
  2. security_optimizer.py — RL, additive only, never authoritative. Learns, per (rule_id, source) pair, whether that SPECIFIC pattern on that SPECIFIC surface has tended to be a real concern or a nuisance — from REAL user yes/no answers on flagged confirmations, nothing synthetic. Surfaces an optional note; never changes whether a rule fires, and is never consulted for the 🔴 RISK tier at all (RISK always blocks, unconditionally, before this layer is even reached). Durable across restarts via framework/bandit_persistence.py.

Two gates, both real, both tested

  • native_agent.security_precheck() — a hard block on the user's own prompt, BEFORE any tool runs: credential/token exfiltration requests, bulk data-exfiltration requests, explicit "skip confirmation" instructions. Same early-refusal shape as llm/guardrails.py's narrower input_guard(), at the identical point in all four framework tracks (native/langgraph/adk/claude — §6.5 equivalence).
  • native_agent.requires_confirmation()/confirm_prompt_for() — every write action (destructive PM action, MCP tool, per-user OAuth MCP tool, or a Google write tool — draft_email/send_email/ create_calendar_event/send_chat_message) requires an explicit yes/no, showing the EXACT arguments, before it runs. A 🟡-flagged write action additionally shows security_optimizer's learned note, if it has one yet.

Gmail/Calendar/Chat's specific threat surface

Connecting a Google account (/account/integrations) hands the assistant real capability inside a real inbox/calendar/chat. What that means concretely:

  • Indirect prompt injection via email/calendar/chat content — security_guard.py's SEC-INJECTION-EMBEDDED rule treats an instruction found INSIDE fetched content (not typed by the user) as automatically 🔴 RISK, more severe than the identical phrase typed by the user directly (🟡) — the assistant never treats "content it read" as "an instruction it should obey."
  • Phishing/social-engineering content — flagged 🟡 so a human reviews it, never auto-acted-on (there's no tool that would let the assistant itself wire money or hand over credentials in response to an email asking for them).
  • Credential/token exposure — SEC-CRED-EXFIL-REQUEST/ SEC-CRED-IN-CONTENT — blocked outright if it's the user asking directly; flagged if it shows up in fetched content.
  • Google Chat's real API limitation (not a security control, but a real constraint worth knowing): there's no way to resolve a plain email address to a Chat user without the People/Directory API and its own separate scope — send_chat_message requires a real space or user resource id, and refuses a plain email with a clear error rather than guessing or silently failing. See services/google_api.py's _resolve_chat_space docstring.

Admin Security Dashboard & Daily Report

Every 🟡/🔴 flag isn't just shown to the user who triggered it — it's also durably logged (app/security_events.py, a new SecurityEvents table, same PK/SK document store every other durable table in this system uses) and made visible to Admins, org-wide, at /admin/security in the PM frontend. 🟢 Safe replies are never logged — the dashboard stays real signal, not a copy of every chat turn.

What an Admin sees: - Recent events (last 7 days, configurable) — who, when, which flag, which rule(s) fired, and a short excerpt of the flagged content — across every user in the organization, not just their own. - A daily report — app/security_report.py aggregates a given day's events (risk count, needs-review count, which users were affected) and generates a genuine LLM-written summary via the same get_llm_client("bulk") call every other background-summarization feature in this codebase uses (agent/memory.py's session-summary fold is the closest analog) — never a fabricated "all clear" when the event list is non-empty; the prompt explicitly forbids inventing, adding, or omitting an event. If every LLM provider is unreachable, a real, honest, non-LLM fallback summary (event/risk counts, affected users) is shown instead of failing — see security_report._fallback_summary. - Reports are cached per calendar day (GET .../daily-report?date=...) and only regenerated on an explicit "Regenerate report" click (?refresh=true) or the first time a given day is viewed — so loading yesterday's report twice doesn't re-summarize it twice.

Access control: Admin role or above (require_role("Admin"), auth.py's ROLE_ORDER) — a Member or Manager gets a real 403, not a watered-down empty view.

What this is NOT: a moderation tool. Nothing here lets an Admin edit, suppress, or act on a flagged conversation from the dashboard — it's read-only visibility, matching the confirmation gate's own philosophy that a human, specifically the person the conversation belongs to, is the one who decides whether a flagged action proceeds. The dashboard's job is oversight and pattern-spotting (a user hitting repeated risk-tier flags is worth a real conversation), not remote control of someone else's chat.
