SLM Coding Test Suite

scripts/run_slm_test_suite.py — 105 real coding prompts run against a named provider (default ollama-coder), each scored for pass/fail, latency, token usage, and a set of cheap deterministic quality checks.

Categories

Category Count What it exercises
generate 30 New code from scratch — functions, classes, a FastAPI endpoint, a Dockerfile, an async fetcher
debug 25 Real, specific bugs (race conditions, off-by-one, mutable defaults, silent exception swallowing, a multi-symptom incident)
refactor 15 Structural changes required to preserve exact behavior
test 15 Writing tests, including edge cases and mocking
repo_analysis 10 Repository-wide questions (TODOs, env vars, security review across a whole codebase)
general_coding 10 Plain knowledge/reasoning questions, deliberately NOT keyword-matched by the intent reasoner — the fallback bucket needs its own coverage too

These are the same six categories llm/intent_reasoner.py classifies into (see README_SLM_REASONING_LAYER.md) — the suite and the reasoning layer share one taxonomy on purpose.

Running it

Needs a reachable provider — run inside ak-chatbot (has the real network path to ak-ollama and every hosted provider's API keys):

docker exec ak-chatbot python -m scripts.run_slm_test_suite \
    --provider ollama-coder --domain coding --out /srv/data/slm_test_report.json
  • --provider — any provider key from llm/router.py (default ollama-coder). Point it at a hosted model instead to get a comparison baseline.
  • --timeout — per-prompt timeout in seconds (default 90 — several of these prompts genuinely ask for long, detailed answers; see README_COMPLEX_EXAMPLE_TRAINING.md's own note on this).
  • --out — where to write the JSON report.

Calls llm.router.call_provider_directly() — the SAME "bypass every tier/chain/bandit, get the NAMED provider's own real answer or a clear error" mechanism scripts/log_complex_ground_truth.py uses, for the identical reason: a silent substitute from TierClient's own fallback chain would make this "the SLM's own test report" in name only.

How pass/fail is decided

A prompt passes when: the call didn't error, the response is non-empty, and (if it contains a fenced code block) that code parses as valid Python. This is a real, reproducible, mechanical check — not a judgment call — and it is not a claim that the code is correct, only that it exists and parses. Reading response_preview (the first 400 characters of each answer, in the JSON report) is still how you'd judge whether an answer is actually good.

What the report contains

{
  "provider": "ollama-coder",
  "summary": {
    "total_prompts": 105,
    "passed": 91,
    "pass_rate": 0.867,
    "avg_latency_ms": 4820.3,
    "p95_latency_ms": 21400.0,
    "intent_reasoner_accuracy": 0.94
  },
  "by_category": { "generate": {"total": 30, "passed": 28, "avg_latency_ms": 3900.1}, ... },
  "results": [ {"id": "GEN-01", "category": "generate", "passed": true,
                "latency_ms": 210.4, "prompt_tokens": 42, "completion_tokens": 88,
                "response_preview": "...", "quality_notes": [] }, ... ]
}

intent_reasoner_accuracy is a live check that llm/intent_reasoner.py's classifier agrees with this suite's own human-assigned category for each prompt (excluding general_coding, which is the deliberate fallback bucket, not something the classifier is expected to "detect").

Honest limits

  • The quality check is deterministic and cheap, not a judge model — it catches "didn't answer" and "the code doesn't parse," not "the code is wrong in a way that still parses." Real quality assessment still needs a human (or a real LLM-judge pass, not built here) reading response_preview/the full response.
  • Results depend on server load, network conditions, and (for a local SLM) whether the model was already warm (see providers.py's OLLAMA_KEEP_ALIVE) — a report run cold will show materially worse avg_latency_ms than one run warm. Compare reports run under the same warmth conditions, not a cold run against a warm one.
  • This tests ONE provider's raw answers via call_provider_directly — it does not exercise CodingAgent's tool-calling loop (read_file/ write_file/run_code), Auto Hybrid's routing decision, or the approval-bar UI. It answers "can this model produce a good ANSWER to these prompts," not "does the whole agent pipeline work end to end" — that's what a live, manual demo run (or a browser/VS-Code-driven integration test) is for.
