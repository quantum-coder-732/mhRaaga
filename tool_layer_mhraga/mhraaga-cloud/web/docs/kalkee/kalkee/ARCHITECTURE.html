Kalkee Architecture — layers, algorithms, and the math behind them

This document goes one level deeper than README.md's tour: every layer Kalkee is built from, the exact per-task algorithm, and the formulas behind adaptive routing (Thompson Sampling), fair multi-agent credit assignment (the Shapley value), the reward/feedback loop, and how the pre-existing PM chatbot's own framework picker (native/langgraph/adk) composes with Kalkee's agent-level router instead of being replaced by it. Plain-text arrow diagrams throughout — no rendering step needed to read this.

1. The full stack, top to bottom

Kalkee adds THREE layers above what already existed (Adaptive Router, Agent Network, Workflow Engine) and reframes the PM chatbot's own machinery (framework picker, model tier chain, session memory) as what sits underneath one specific registered agent (pm-agent), not the whole system:

2. Where the pre-existing PM chatbot fits

Nothing about the PM domain's own machinery changed — pm-agent is a thin wrapper (framework/agents/pm_agent.py) around the exact same get_agent(framework).handle_message(...) call POST /api/chat/message already used. Its own internal per-turn algorithm — unchanged — still runs entirely INSIDE the "AGENT EXECUTION → pm-agent" box above:

load_session(user, session_id)
  ▼
framework_stats.choose() ──► pick native | langgraph | adk   (a SEPARATE,
  ▼                                                            lower-level
classify_task_complexity(msg) → tier                          bandit than
  ▼                                                            Kalkee's own
get_llm_client(tier, preferred) → provider chain               agent router
  ▼                                                            — see §5)
perceive_intent → resolve_entities → confirm-if-destructive → execute → format
  ▼
persist_session + record framework stats
  ▼
reply ──► back up through pm_agent.respond() ──► Kalkee's own
                                                   evaluate()/feedback loop

Two bandits, two different jobs, cleanly stacked:

  Kalkee's AdaptiveRouter          "Which AGENT should answer this task —
  (router.py)                      pm-agent, coding-agent, openclaw-agent,
                                    or a new one someone just registered?"
         │
         ▼ (if pm-agent was picked)
  the PM domain's framework_stats  "Now that pm-agent is answering, which
  (agent/framework_stats.py)        TRACK should run it — native,
                                     langgraph, or adk?"

The PM domain's native/langgraph/adk picker never disappears or gets subsumed — it's a strategy decision happening one level BELOW Kalkee's own, for exactly one agent, exactly as it always has.

3. The Adaptive Agent Assignment Engine — Thompson Sampling

Modeled as a linear contextual bandit (Agrawal & Goyal, "Thompson Sampling for Contextual Bandits with Linear Payoffs", ICML 2013). Per agent a, Kalkee keeps a Bayesian linear regression posterior over reward given context:

observe (context x, reward r) pairs over time
        │
        ▼
  B_a  =  Σ x·xᵗ  +  λI          (posterior precision matrix, λ = ridge prior)
  f_a  =  Σ r·x                  (posterior weighted-reward sum)
        │
        ▼
  μ_a  =  B_a⁻¹ f_a              (posterior MEAN weight vector)
  Σ_a  =  ν² · B_a⁻¹             (posterior COVARIANCE, ν = exploration scale)

Selecting an agent for a NEW task with context vector x(T):

for each candidate agent a:
        θ_a  ~  N(μ_a, Σ_a)              ← SAMPLE a weight vector (the "Thompson" step)
        score(a)  =  θ_a · x(T)          ← predicted reward under this sample
        ▼
selected  =  argmax_a  score(a)

Sampling a fresh θ_a every time — rather than always using μ_a directly — is what gives Thompson Sampling its exploration: an agent with a wide, uncertain posterior occasionally wins even with a middling mean, so it keeps collecting data instead of being starved by one early bad run. This is the online, γ→0 (single-step) special case of the general RL objective:

π*  =  argmax_π  E[ Σ_t γ^t R_t ]

— sequencing a whole multi-turn task (rather than one agent-pick) is the natural next step, and is deliberately left pluggable (AdaptiveRouter.strategy) for a future Q-Learning/policy-gradient/PPO router without changing any caller.

Cold start — before an agent has ANY real feedback, its posterior is seeded from a hand-designed heuristic instead of zero:

U(a|T)  =  w1·Q(a,T)  +  w2·R(a)  +  w3·C(a,T)  +  w4·F(a,T)  −  w5·Cost(a)  −  w6·Latency(a)
             │            │            │            │              │              │
             │            │            │            │              │              └─ agent.latency_profile
             │            │            │            │              └─ agent.cost_per_call_usd
             │            │            │            └─ reliability_score (no feedback yet, so reused)
             │            │            └─ 1.0 if required_capabilities ⊆ agent.capabilities
             │            └─ agent.reliability_score (registry metadata)
             └─ reliability_score (no per-task quality history yet, so reused)
        │
        ▼
  seed f_a so that  B_a⁻¹ f_a ≈ U(a|T)  on every feature direction
  (B_a = λI initially ⇒ B_a⁻¹ = I/λ ⇒ posterior MEAN starts at U(a|T),
   posterior VARIANCE starts at its WIDEST — easily overridden by the
   first few real outcomes)

Learning step, after every task closes:

observe reward r for agent a on context x
        ▼
  B_a  +=  x·xᵗ
  f_a  +=  r · x
        ▼
  (posterior mean shifts toward actually predicting r for
   contexts shaped like x; posterior narrows ⇒ less exploration
   for THIS agent on THIS kind of task going forward)

4. Fair multi-agent credit — the Shapley value

When more than one agent contributed to a single task (a HierarchicalStep's lead + workers, a SequentialStep's pipeline), only ONE reward is ever observed for the whole task. Dumping all of it on the last agent, or splitting it evenly, both teach the router the wrong lesson. Kalkee instead uses the Shapley value — Lloyd Shapley's 1953 cooperative-game-theory solution concept, for which he shared the 2012 Nobel Memorial Prize in Economic Sciences (with Alvin Roth, "for the theory of stable allocations and the practice of market design").

Characteristic function — a coalition's value is the probability at least one member did a good-enough job (a noisy-OR over standalone quality scores):

v(S)  =  1  −  Π_{i ∈ S} (1 − quality_i)

Agent i's Shapley value averages its marginal contribution over EVERY possible arrival order:

                        |S|! · (|N|-|S|-1)!
φ_i(v)  =  Σ_{S ⊆ N\{i}} ───────────────────  ·  ( v(S ∪ {i}) − v(S) )
                               |N|!

  every subset S of "the others"
        │
        ▼
  weight(S)  =  |S|! (n-|S|-1)! / n!     ← how likely S is exactly who
        │                                  arrived before i, over ALL orderings
        ▼
  marginal(S)  =  v(S ∪ {i}) − v(S)      ← what i ADDED given S already there
        │
        ▼
  φ_i  =  Σ_S  weight(S) · marginal(S)

Exact for ≤8 agents (2⁸ = 256 subsets, trivial); a Monte Carlo permutation estimator (shuffle order, accumulate each agent's marginal as it's "added" to a running coalition, average over many shuffles) for more, the same approximation SHAP-style tools use at scale.

Efficiency axiom (verified in tests/test_gmaofn_core.py): Σ_i φ_i = v(N) — every unit of value is attributed to someone, none invented or lost — so multiplying each φ_i / v(N) share by the task's ACTUAL observed reward gives every agent its fair, attributed reward directly:

attributed_reward(i)  =  total_reward  ×  φ_i / Σ_j φ_j

5. Reward, adaptive weights, and the closed loop

R  =  α·Quality  +  β·Success  +  γ·UserFeedback  −  δ·Cost  −  ε·Latency  −  ζ·Failure

UserFeedback defaults to the agent's own self-evaluated quality until a real human rating arrives (POST /api/v1/feedback), at which point that task's reward is RECOMPUTED with the human score standing in, and a SECOND router update is applied — real feedback outranks self-assessment without discarding it.

α..ζ adapt online (not fixed forever): after every task, each coefficient nudges toward whichever term actually correlated with a HIGH observed reward, and away from whichever moved opposite it — a transparent, single-line-per-term update, not a second hidden model:

for each term (quality, success, user_feedback, cost, latency, failure):
        signal  =  that term's own value on THIS outcome, in [0,1]
                   (cost/latency inverted: LOW cost/latency ⇒ HIGH signal)
        ▼
        delta  =  learning_rate × reward × (signal − 0.5)
        ▼
        weight  +=  delta         (never below a small floor — always explorable)
        ▼
renormalize all six weights to sum to 1

The full closed loop, end to end:

Task
  ▼
Adaptive Router selects agent(s)                 (§3)
  ▼
Workflow Engine executes them                     (SequentialStep / ParallelStep / ...)
  ▼
Result  +  self-evaluated quality per agent
  ▼
Shapley credit attribution                         (§4)
  ▼
Reward calculation                                  R = α·Q + β·S + γ·F − δ·C − ε·L − ζ·Fail
  ▼
Router posterior update PER AGENT                    (its own Shapley-attributed share)
  ▼
Adaptive weight update                                  (α..ζ nudge toward what tracked reward)
  │
  └──────────────────────────────────────────────────────► improved routing on the NEXT task
                              ▲
                              │
              (optional, later)  POST /api/v1/feedback
                              │       a human rates this task
                              └── recompute reward with that rating,
                                  re-attribute via Shapley, update AGAIN

7. Model optimization strategies — where they actually live

None of these six strategies run inside Kalkee's Python process — they're properties of the inference server behind whichever model-layer provider answers (llm/providers.py's CustomProvider/HuggingFaceProvider/OpenAICompatible), fixed at that server's own startup, not something a per-request HTTP call can add after the fact. What DOES run in-process, on every single model call, is a second, faster-cycling Thompson Sampling bandit (llm/optimization_router.py's OptimizationRouter, reusing framework/bandit.py's exact same math as the agent-level router) choosing which REAL request-level parameter combination — temperature, max tokens, top_p/top_k — to send, learned from that call's own latency/success. Two honest, separate layers, composed:

  Kalkee (this process)                              Inference server (vLLM / TGI / etc.)
  ──────────────────────                              ─────────────────────────────────────
  OptimizationRouter.select(provider, tier)
        │  Thompson Sampling over a FEW real arms
        │  ("balanced" / "low_latency" / "high_quality" —
        │   llm/optimization_router.py's DEFAULT_ARMS)
        ▼
  provider.extra_body  ←  merged with the winning arm
        │  (temporarily, restored right after this ONE call —
        │   see TierClient.chat()'s try/finally)
        ▼
  CustomProvider.chat(messages, tools)
        │  HTTP POST /chat/completions  (temperature=…, top_p=…, …)
        └────────────────────────────────────────────►  request enters the server's
                                                          scheduler/batching/attention/
                                                          parallelism stack — the SIX
                                                          strategies below this line are
                                                          all fixed server config,
                                                          invisible to the HTTP contract
        ◄────────────────────────────────────────────  response
        ▼
  OptimizationRouter.update(provider, arm, tier,
                            ok=..., latency_ms=...)
        │  this call's own outcome feeds the bandit —
        └──────────────────────────────────────────► improves the NEXT call's arm choice

OptimizationProfile (llm/optimization.py) is the OTHER half — purely declarative metadata an operator sets once (CUSTOM_MODEL_OPTIMIZATION/ HUGGINGFACE_OPTIMIZATION env vars, or an EXTRA_LLM_PROVIDERS entry's "optimization" field) describing which of the six strategies THAT server is actually deployed with — surfaced via GET /api/v1/models, never consulted to decide how a request is made. Setting tensor_parallel_size=4 there does not itself shard anything; it records that the server behind that URL already is sharded, for observability.

KV cache — every generated token's attention key/value tensors are cached so each new token only computes attention against the cache instead of recomputing the whole sequence:

prompt tokens ──► compute K,V for each ──► CACHE
        ▼
generate token 1 ──► attend against CACHE ──► append token 1's K,V to CACHE
        ▼
generate token 2 ──► attend against CACHE (now longer) ──► append ...
        ▼
        ⋯ (cost per token stays ~constant instead of growing with sequence length)

vLLM's PagedAttention manages this cache in fixed-size non-contiguous "pages" (like OS virtual memory) instead of one giant pre-allocated buffer per request — the mechanism that also makes continuous batching below practical at high concurrency.

Continuous batching — requests join and leave a running batch at the token-generation granularity, not the request granularity:

classic (static) batching:            continuous batching:
┌──────┬──────┬──────┐                ┌──────┬──────┬──────┐
│ req A│ req B│ req C│  ← whole        │ req A│ req D│ req C│  ← req B finished
│  gen │  gen │  gen │    batch          │  gen │ (new)│  gen │    early, req D
│ step │ step │ step │    waits           │ step │ join!│ step │    slots in
└──────┴──────┴──────┘    for the        └──────┴──────┴──────┘    IMMEDIATELY,
   (B finishes early,     SLOWEST                                   no idle GPU
    GPU idles until       request                                   time wasted
    A and C finish)       to finish

Speculative decoding — a small, fast "draft" model proposes several tokens ahead; the big model verifies them all in ONE forward pass instead of one pass per token:

draft model proposes: [tok1, tok2, tok3, tok4]   (fast, cheap, maybe wrong)
        ▼
target model verifies ALL FOUR in one batched forward pass
        ▼
accept the longest correct PREFIX (say tok1, tok2 match; tok3 doesn't)
        ▼
keep [tok1, tok2], target model generates the real tok3 itself, repeat
        │
        └─ net effect: multiple tokens' worth of output for close to the
           cost of ONE target-model forward pass, whenever the draft
           model guesses right (draft/target agreement rate governs the
           actual speedup)

Optimized attention mechanisms — FlashAttention (fuses the softmax(QKᵗ/√d)V computation into one GPU kernel, avoiding materializing the full attention matrix in memory) and PagedAttention (KV cache paging, above) are the two most widely deployed; both are transparent to the API — same request/response shape, different GPU kernels underneath.

Model parallelism — splitting a model too large for one GPU/node across several, three different ways:

Tensor parallelism:            Pipeline parallelism:          Data parallelism:
split EACH LAYER's             split the model's LAYERS       full model copy on
matrices across GPUs             across GPUs — GPU 1 has        EACH GPU — different
(GPU 1 has half the weight        layers 1-10, GPU 2 has         REQUESTS routed to
matrix, GPU 2 the other            layers 11-20, ...                different replicas,
half) — every layer's                token flows through            not one request
forward pass is itself             GPU 1 then GPU 2 then...          split across GPUs
split, GPUs sync per layer

Combining approaches — a production vLLM/TGI deployment typically runs ALL of these together, not one at a time:

incoming requests
        ▼
continuous batching scheduler ── admits/evicts requests per token step
        ▼
PagedAttention KV cache ── shared, paged cache across the whole batch
        ▼
tensor parallelism ── each layer's matmul split across N GPUs in this node
        ▼
pipeline parallelism ── (if the model doesn't fit tensor-parallel alone)
                          different layer ranges on different nodes
        ▼
speculative decoding ── a small draft model proposes, the (already-
                          parallel, already-batched) target model verifies
        ▼
data parallelism ── multiple full replicas of the ENTIRE stack above,
                      load-balanced across requests, for raw throughput
                      beyond what one replica's GPUs can serve
        ▼
response ──► back through CustomProvider.chat() ──► Kalkee, none the wiser
              about which of the above actually ran

For the six SERVER-side strategies, Kalkee's own job stops at "know the endpoint, send the request, read the response" — configuring vllm serve --tensor-parallel-size 4 --speculative-model <draft> (or TGI's equivalent flags) is a deployment decision made once, outside this codebase, for whichever CUSTOM_MODEL_BASE_URL/HUGGINGFACE_ENDPOINT_URL a Kalkee deployment points at. What Kalkee DOES actively decide, every single call, on top of whatever server sits behind that URL, is which real request-level parameter arm to send — the OptimizationRouter described above.

8. The SLM Generation Layer — hybrid routing, token trimming, nightly self-improvement

§7's six strategies are all things Kalkee points AT but never touches — config baked into somebody else's inference server. The SLM Generation Layer (Ollama, OLLAMA_BASE_URL/OLLAMA_MODEL in config.py, plus everything in README_SLM_GENERATION_LAYER.md) is the one model in the whole tier chain Kalkee's own process actively manages end to end: collecting the enterprise prompts and grounded ground truth it should learn from (§8.3 step 0 below), whether to even use the local model this turn, how to fit the PM tool schema into its smaller context window, and — the one loop in this entire document that isn't a bandit — a nightly job that rewrites its actual weights and produces a real, standalone, branded artifact: Algo-Kalkee-SLM.

How it connects back into everything above: the artifact this layer produces is registered via POST /api/admin/providers with a tiers field (§8.3 step 3f), which llm/router.py's _effective_chains() splices directly into the SAME realtime/bulk/delay_ok fallback chains §1's MODEL ABSTRACTION LAYER box shows — so every one of Kalkee's 9 default agents (§1's AGENT EXECUTION box) can be routed to Algo- Kalkee-SLM through the ordinary get_llm_client(tier, ...) call, with no orchestrator-side code change and no restart. This layer only ever produces a candidate for that shared model abstraction layer — it never bypasses the Adaptive Router, the Workflow Engine, or Shapley credit above it.

8.1b Domain mode — choosing AMONG local SLMs, not just local-vs-hosted (llm/domain_router.py)

A fourth selectable mode, alongside Auto / one specific model / Hybrid: where §8.1 decides local-vs-hosted by CHEAP COMPLEXITY features, Domain mode decides WHICH of possibly several registered domain-specific Algo-Kalkee-SLM variants (README_SLM_GENERATION_LAYER.md §5) a message is about, by CONTENT:

 domain_router.registered_domains()  ── live discovery, by naming
        │                               convention "algo-akanade-slm-<domain>"
        ▼
 arm_ids = ["general"] + every registered domain   (dynamic — a new
        │                                            domain SLM needs
        ▼                                            zero code changes)
 per arm: LinearBanditCore.score(arm, [word_count, clause_count, tier])
     + TaskMemory.bonus_for(message, arm)  ── embedding similarity to
        │                                     past (query, arm, reward)
        ▼                                     triples — folded into
 argmax → winner                              EVERY decision here, not
        │                                     just used as a one-time
        ▼                                     cold-start seed the way
 preferred = "algo-akanade-slm-<winner>"      §3's utility_prior is
        │        (or None for "general")
        ▼
 TierClient.preferred, same LOCAL_TIMEOUT_SECONDS escalation as §8.1
        │
        ▼
 record_outcome(success) → updates BOTH the bandit AND the memory

Why TaskMemory carries the real weight here (unlike §3's agent selection, where it's a cold-start-only nudge on top of TaskContext's already-structured task_type signal): a domain SLM has no such structured per-arm feature available — the accumulated embedding memory of which past queries worked well on which domain IS the signal, so it has to inform every decision, not just the first one.

8.2 Trimming the tool schema to fit the local model's context (llm/token_optimizer.py)

Runs only when the answering provider's name starts with "ollama" — hosted models get the full PM tool schema unconditionally:

        │                                               NEVER trimmed, any level)

8.4 The same harness, two jobs: picking a model AND gating its nightly update

scripts/eval/'s candidate-selection pipeline is built once and reused twice — deciding which local model to START with, and (§8.3 step 3e) gating whether a fine-tuned version is actually an improvement before it ever reaches a real user:

 eval/test_assets/*.yaml (gold + rubric, 32 items)
        +
 eval/candidates.yaml (local Ollama tags + OpenRouter candidates,
                        hosting: local|cloud, explicit)
        │
        ▼
 harness.py — for each (candidate, item):
    deterministic (exact/regex/schema)  ──or──  llm_judge (bias guard:
                                                  never told which model answered)
        │
        ▼
 human_sample.py — ~12% sample, weighted to reasoning/planning/complex_reasoning
        │
        ▼
 aggregate.py — score matrix × eval/weights.yaml (locked in BEFORE
    scoring), latency p50/p95, $/1k requests
        │
        ▼
 decide.py — ranked top 1-2, cost/latency-adjusted, + manual
    license/vLLM-TGI checklist (deliberately not automated)
        │
        ▼
 regression_gate.py — same harness, reused NIGHTLY (§8.3 step 3e) for
    the cheap two-candidate (base-tag vs new-tag) PEFT promotion check

Capacity planning, not a runtime optimizer: llm/memory_estimator.py answers "will this fit on my hardware" for both real local-compute paths above — Ollama inference and the nightly LoRA job itself — using the standard transformer memory-sizing formulas (full derivation in README_MEMORY_MANAGEMENT.md). An operator tool run before choosing hardware or a model size, not something in the request-time path.

Why none of this touches the hosted rungs: every one of §8.1-8.3 is gated on either an explicit provider="hybrid" selection or a provider name starting with "ollama" — a deployment with no OLLAMA_BASE_URL configured never routes through any of this, and a hosted-only turn's tool schema, timeout, and fine-tune eligibility are completely unaffected by whether Ollama is configured at all.

9. PEFT Analyzer, RL-weighted routing, and the Trading Agent

Three additions on top of §8's pipeline, full detail in their own docs (README_PEFT_ANALYZER.md, README_TRADING_AGENT.md, README_CODING_AGENT.md):

  • PEFT Analyzer (app/agent/peft_analyzer.py) — scrapes admin-configured Wikipedia topics into real ground-truth training pairs (via the existing finetune_log.log_ground_truth_turn(), no new data format), run by deploy/nightly_finetune.sh before the fine-tune loop. Local blobs capped (default 40GB), oldest-evicted.
  • "Auto" now benefits from domain-SLM routing too: llm/domain_ router.py's bandit (previously only consulted on an explicit provider="domain" pick) is now ALSO consulted on a plain auto turn in native_agent.py/langgraph_agent.py/adk_agent.py — a genuinely-winning fine-tuned SLM gets a real chance to answer without anyone asking for Domain mode by name. Both domain_router.py and llm/provider_optimizer.py now persist (bandit_persistence.py) and expose stats() via GET /api/v1/metrics/routing — "who's winning for what," visible in PeftMetricsDashboard.tsx.
  • "Train this" from chat (app/agent/peft_training_tool.py) — a user can say "train the trading model on this" (pasted text or a URL); native_agent.resolve_arguments asks which domain via the same clarify()/resume_clarification round trip every ambiguous PM request already uses if it wasn't named, then logs a real ground-truth example to that domain's own log file (finetune_log.py's domain= param, matching deploy/nightly_finetune.sh's existing per-domain <domain>_ turns.jsonl convention). Actual training still only runs on the nightly schedule. Shared across all three chat tracks since they all call the same native_agent.resolve_arguments/requires_confirmation.
  • Trading Agent (app/agent/trading_tools.py) — fetch_price_ history/run_backtest (real Yahoo Finance data, a vectorized moving-average-crossover backtest, no lookahead bias) added as tools in the SAME shared tool-calling pipeline (agent/tools.py) the PM Tool already uses — reachable from web/mobile/VS Code with zero new endpoint or UI wiring, since none of them call the separate app/framework/ multi-agent registry POST /api/v1/orchestration/ execute reaches (investigation found neither web nor mobile ever call that endpoint — only the VS Code extension does).
  • Security Dashboard, made real: the three static-analysis security agents (code_security_agent.py/supply_chain_agent.py/ cloud_config_agent.py) now persist every scan (security_findings. log_scan(), including clean ones) instead of the findings existing only inside that one call's AgentResult — GET /api/admin/security/ findings and AdminSecurity.tsx's new "Threats & vulnerabilities identified" table are the dashboard view.
